## ERP-K. Master Data

- [ ] ERP-K1. Units of measure and conversions are controlled and effective-dated if necessary.
- [ ] ERP-K2. Items that must be integer-only cannot receive fractional quantity unless allowed.
- [ ] ERP-K3. Warehouses and internal locations distinguish receiving, quarantine, damaged, WIP, production, and shipping states.
- [ ] ERP-K4. Tax rules have effective dates.
- [ ] ERP-K5. Exchange rates are historical.
- [ ] ERP-K6. Document numbering rules are controlled and auditable.
- [ ] ERP-K7. Master-data changes affecting finance/costing require approval where appropriate.

## ERP-L. Segregation of Duties (SoD)

Verify that one user cannot perform conflicting end-to-end fraud-capable workflows unless explicitly authorized and monitored.

- [ ] ERP-L1. Create supplier + approve PO + receive goods + approve invoice + pay supplier.
- [ ] ERP-L2. Create customer + change credit limit + approve sale + issue credit note.
- [ ] ERP-L3. Modify price list + approve discount + invoice.
- [ ] ERP-L4. Create inventory adjustment + approve own adjustment.
- [ ] ERP-L5. Create journal + approve/post same journal.
- [ ] ERP-L6. Modify BOM/cost + approve production variance.
- [ ] ERP-L7. Quality inspector cannot bypass own rejection without independent approval.

Build a **conflict matrix**, not merely a list of hundreds of permissions.

## ERP-M. Audit Trail

- [ ] ERP-M1. Critical changes are append-only.
- [ ] ERP-M2. Audit records contain actor, time, old value, new value, reason, correlation ID, and source.
- [ ] ERP-M3. DB admins cannot silently rebuild the audit chain without detection, if tamper evidence is claimed.
- [ ] ERP-M4. Cryptographic audit chains use keyed/tamper-evident protection where required.
- [ ] ERP-M5. System time manipulation is considered.
- [ ] ERP-M6. Exported audit evidence is reproducible.

## ERP-N. Reports & Reconciliation

For every dashboard KPI, write the exact accounting/business definition before accepting it.

- [ ] ERP-N1. Sales report = posted sales transactions under an explicit date/currency/cancellation rule.
- [ ] ERP-N2. Inventory report = movement ledger / reconciled balance, not an occasionally updated cached field.
- [ ] ERP-N3. Inventory valuation report = valuation engine layers/method, not quantity × current item price.
- [ ] ERP-N4. AP/AR aging reconciles to GL control accounts.
- [ ] ERP-N5. Production cost report reconciles to inventory/WIP/variance postings.
- [ ] ERP-N6. Dashboard totals reconcile to underlying detail.
- [ ] ERP-N7. Reports are tested across period close, returns, reversals, partial transactions, and multiple currencies.

# 4. Mandatory Adversarial Scenario Pack

An AI auditor should actively attempt these scenarios where relevant.

## General scenarios
1. Send the same POST request twice with the same idempotency key.
2. Send the same request twice without the key and verify business safeguards.
3. Timeout the client after server commit, then retry.
4. Kill the backend during a multi-step transaction.
5. Kill the database during commit.
6. Fail object storage after DB write.
7. Succeed object upload but fail DB commit.
8. Fail third-party API after local state update.
9. Perform two simultaneous updates to the same record.
10. Access another tenant's object by changing ID.
11. Call admin endpoint as ordinary user.
12. Upload malicious/invalid file type.
13. Generate CSV containing formula payload.
14. Query a large reporting period under transactional load.
15. Restore backup to a clean environment.

## ERP scenarios
16. Receive goods today; supplier invoice arrives next week.
17. Receive 100 units, invoice only 70.
18. Select FIFO, receive at 10 then 15, issue partial quantity, verify exact layers.
19. Use FEFO operationally while valuing financially with FIFO.
20. Reserve same limited stock for two orders concurrently.
21. Issue 40% of a manufacturing order, complete remaining 60% later.
22. Substitute a BOM component and verify costing/variance.
23. Reject a lot in quality and attempt sales issue.
24. Reverse a posted journal from a closed prior period.
25. Backdate an inventory receipt into a closed period.
26. Change valuation policy and verify historical postings are not silently rewritten.
27. Process purchase return after partial consumption.
28. Process sales return and verify cost restoration/reversal.
29. Trace a finished batch back to all supplier lots.
30. Recall a supplier lot and identify affected customers.

# 5. AI Audit Procedure

## Phase 1 — Inventory the system
Collect:
- repository tree,
- architecture,
- framework versions,
- database schema,
- migrations,
- environment configuration,
- background jobs,
- third-party integrations,
- authentication model,
- authorization model,
- file storage,
- deployment topology,
- backup process,
- monitoring,
- test suites.

Do not start by reviewing styling or frontend polish.

## Phase 2 — Identify critical business invariants
Create an invariant table:

| Invariant | Where enforced | Test proving it | Failure severity |
|---|---|---|---|
| Example: journal debit = credit | DB deferred constraint | integration test X | Critical |

Any Critical invariant with no enforcement or no test is a finding.

## Phase 3 — Trace critical workflows end-to-end
For each business workflow, map:

`User Action -> API -> Validation -> Authorization -> DB Transaction -> Side Effects -> Queue/Outbox -> Audit -> Report Impact`

Identify every point where partial failure can create inconsistent state.

## Phase 4 — Inspect database before UI
Review:
- schema,
- constraints,
- indexes,
- unique keys,
- foreign keys,
- transaction boundaries,
- triggers/procedures,
- RLS,
- migrations.

## Phase 5 — Security abuse review
Attempt negative authorization and tenant-isolation tests.

## Phase 6 — Concurrency review
Find all shared mutable resources and test contention.

## Phase 7 — Recovery review
Prove backup restore, retry behavior, crash recovery, and orphan cleanup.

## Phase 8 — Report reconciliation
Pick representative KPIs and independently recompute them from source transactions.

## Phase 9 — AI-generated-code review
Search for:
- TODO,
- FIXME,
- mock,
- placeholder,
- stub,
- fallback,
- temporary,
- `catch {}`,
- swallowed exceptions,
- hardcoded roles,
- hardcoded tenant IDs,
- floats used for money,
- client-only permission checks,
- duplicated validation,
- raw SQL,
- disabled tests,
- skipped tests,
- insecure defaults.

## Phase 10 — Production readiness verdict
Use the scoring model below.

# 6. Severity Model

## Critical
Can cause:
- money/inventory corruption,
- unauthorized data access,
- cross-tenant leak,
- irreversible data loss,
- duplicate payment/order/stock movement,
- false statutory/financial result,
- inability to restore after disaster,
- silent use of wrong business algorithm.

## High
Can cause major outage, serious business inconsistency, privilege abuse, or large-scale incorrect results but has a practical recovery path.

## Medium
Can cause operational friction, localized inconsistency, performance degradation, or maintainability risk.

## Low
Minor engineering quality, documentation, observability, or UX issue with limited operational impact.

# 7. Readiness Score

Do not average away Critical findings.

### Gate first
- Any unresolved Critical -> **FAIL / NOT PRODUCTION READY**
- 3+ unresolved High in one critical workflow -> **FAIL / NOT PRODUCTION READY**

### Then score
- Security & Authorization: 20%
- Data Integrity & Transactions: 20%
- Reliability & Recovery: 15%
- Testing & Concurrency: 15%
- Architecture & Maintainability: 10%
- Performance & Observability: 10%
- Deployment & Supply Chain: 10%

For ERP add:
- Accounting & Inventory Integrity must independently score >= 90%.
- Manufacturing/Quality/Traceability must score >= 85% if those modules are claimed.

### Verdict bands
- 95–100: Production Ready with low residual risk
- 90–94: Conditionally Ready; close remaining High/Medium findings
- 80–89: Pre-production; significant hardening required
- 60–79: Prototype / Beta only
- <60: Unsafe architecture or implementation

Critical findings override score.
