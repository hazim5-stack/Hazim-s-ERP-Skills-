# Hazim Batwa's Engineering Skill for Reviewing a Mini ERP Project for Small and Micro Businesses

## Purpose
Use this skill to perform an adversarial engineering audit of an existing ERP or enterprise operations project before it is considered production-ready.

It is specialized for ERP / manufacturing / finance-heavy systems: inventory, accounting, purchasing, sales, manufacturing, quality, costing, traceability, multi-tenant enterprise SaaS, and multi-role operational workflows.

General software checks remain in this skill because ERP correctness depends on architecture, security, database integrity, distributed workflows, performance, observability, backups, and supply-chain integrity.


> **Scope boundary:** This skill audits an existing ERP implementation. For greenfield design or pre-build architecture, use **ERP Project Planning Skill** first.

The goal is not to praise the codebase. The goal is to find failure modes that can cause:
- incorrect data,
- silent financial errors,
- security breaches,
- duplicate transactions,
- race conditions,
- corrupted state,
- broken recoverability,
- false reports,
- operational downtime,
- or misleading "looks finished" software.

---

# 1. Auditor Operating Rules

## 1.1 Default stance
Assume the project is **not production-ready until evidence proves otherwise**.

Do not accept:
- screenshots,
- UI completeness,
- number of tables,
- number of tests,
- number of API routes,
- number of permissions,
- framework names,
- AI-generated claims,
- or developer statements

as proof of correctness.

Require **runtime evidence**.

## 1.2 Evidence hierarchy
Rank evidence from strongest to weakest:

1. Reproducible automated test with deterministic result.
2. Database constraint / invariant that prevents invalid state.
3. Load / concurrency / failure-injection test.
4. End-to-end scenario using realistic data.
5. Logs, traces, query plans, metrics, backup restore evidence.
6. Code inspection.
7. Documentation.
8. Developer claim.
9. Screenshot.

A screenshot alone never closes a critical finding.

## 1.3 Required result for every checklist item
For each item return:

- **Status:** PASS / FAIL / PARTIAL / NOT TESTED / NOT APPLICABLE
- **Severity:** Critical / High / Medium / Low
- **Evidence:** exact file, function, query, migration, test, log, screenshot, trace, or reproduction command
- **Risk:** what can go wrong in production
- **Fix:** minimum safe remediation
- **Verification:** how to prove the fix works

## 1.4 Stop-ship rule
The system must be classified **NOT PRODUCTION READY** if any unresolved Critical issue exists in:

- authorization,
- tenant isolation,
- financial posting,
- inventory integrity,
- irreversible data corruption,
- duplicate payments/orders/stock movements,
- secrets exposure,
- missing backup recovery,
- unsafe migrations,
- or silent fallback that produces wrong business results.

# 2. General Software Project Audit

## A. Architecture & System Boundaries

- [ ] A1. Is there a clear architecture diagram showing frontend, backend, database, cache, queues, file storage, third-party integrations, and trust boundaries?
- [ ] A2. Is each source of truth explicitly defined?
- [ ] A3. Is business logic centralized rather than duplicated across frontend, backend, jobs, and database triggers?
- [ ] A4. Are critical workflows modeled as state transitions rather than loose boolean flags?
- [ ] A5. Are external side effects separated from core database transactions using an Outbox / queue / durable job model where needed?
- [ ] A6. Is the architecture free from single points of failure that contradict the claimed availability requirement?
- [ ] A7. Are failure domains documented?
- [ ] A8. Can the system safely restart halfway through a workflow?
- [ ] A9. Are background jobs idempotent?
- [ ] A10. Are timeout and retry rules explicit for every external dependency?

### Red flags
- Critical operations implemented only in UI logic.
- One request performs DB write + payment + email + file upload synchronously with no recovery design.
- Redis/cache used as the only source of truth for durable business data.
- Hidden business logic scattered across controllers.

---

## B. Data Model & Database Integrity

- [ ] B1. Are primary keys stable and globally safe for the deployment model?
- [ ] B2. Are foreign keys present for real relationships?
- [ ] B3. Are NOT NULL constraints used where null is invalid?
- [ ] B4. Are uniqueness rules enforced in the database, not only in application validation?
- [ ] B5. Are domain invariants enforced using CHECK constraints, triggers, procedures, or equivalent database-level protection where appropriate?
- [ ] B6. Are money values stored as decimal/numeric, never binary floating point?
- [ ] B7. Are timestamps timezone-aware where needed?
- [ ] B8. Is destructive deletion prohibited for immutable financial/audit records?
- [ ] B9. Are soft-delete semantics justified and safe?
- [ ] B10. Are cascades reviewed to ensure one delete cannot destroy unrelated business history?
- [ ] B11. Are migrations forward-safe and backward-aware?
- [ ] B12. Is production schema drift detectable?
- [ ] B13. Are migrations tested against realistic data volume?
- [ ] B14. Are long-running migrations designed to avoid locking the production system?
- [ ] B15. Is historical data meaning preserved when configuration changes later?

### Required adversarial tests
- Insert invalid data directly through SQL/API bypassing frontend validation.
- Execute migration against a production-sized clone.
- Delete or modify referenced records and confirm history remains valid.

---

## C. Transactions, Concurrency & Race Conditions

- [ ] C1. Is every multi-step critical business operation atomic where it must be atomic?
- [ ] C2. Are race conditions identified for counters, balances, inventory, bookings, quotas, seats, payments, and unique resources?
- [ ] C3. Are row locks / optimistic concurrency / serializable transactions used intentionally?
- [ ] C4. Can two simultaneous requests oversell, overbook, double-spend, or reserve the same resource?
- [ ] C5. Are idempotency keys enforced by a unique database constraint?
- [ ] C6. Does retrying after a timeout return the previous result instead of creating a second transaction?
- [ ] C7. Are deadlocks detected, retried safely, and monitored?
- [ ] C8. Are counters derived safely rather than updated with read-modify-write races?
- [ ] C9. Are distributed side effects handled with Outbox / Saga / compensating actions when one DB transaction cannot cover all systems?
- [ ] C10. Are concurrent tests performed on the same logical resource, not only on unrelated rows?

### Minimum evidence
Run realistic contention tests, not only 5–10 concurrent calls. For critical shared resources, test hundreds of overlapping operations and inspect:
- duplicates,
- lost updates,
- deadlocks,
- lock wait,
- balance drift,
- final state consistency.

---

## D. API Correctness & Contracts

- [ ] D1. Are input schemas validated server-side?
- [ ] D2. Are authorization checks independent of client-supplied role/user/tenant IDs?
- [ ] D3. Are API error codes consistent and machine-readable?
- [ ] D4. Are pagination, filtering, sorting, and limits enforced safely?
- [ ] D5. Are mass-assignment vulnerabilities prevented?
- [ ] D6. Are object IDs checked for ownership (IDOR prevention)?
- [ ] D7. Are duplicate submissions safe?
- [ ] D8. Are PATCH/PUT semantics correct and documented?
- [ ] D9. Are API versions or compatibility rules defined for breaking changes?
- [ ] D10. Are webhooks authenticated, replay-protected, and idempotent?

---

## E. Authentication, Authorization & Tenant Isolation

- [ ] E1. Is authentication implemented with current secure practices?
- [ ] E2. Are passwords hashed using a modern password hashing algorithm?
- [ ] E3. Are session/token lifetimes, rotation, revocation, and logout behavior correct?
- [ ] E4. Are secrets excluded from source code, frontend bundles, logs, and error responses?
- [ ] E5. Is authorization enforced server-side for every sensitive action?
- [ ] E6. Is default-deny used?
- [ ] E7. Is tenant isolation enforced at the data layer where possible?
- [ ] E8. Are row-level security / tenant filters tested with negative cross-tenant cases?
- [ ] E9. Can privileged database roles bypass tenant isolation accidentally?
- [ ] E10. Are field-level permissions enforced for sensitive values?
- [ ] E11. Is there a segregation-of-duties model for high-risk operations?
- [ ] E12. Are privilege escalation paths tested?
- [ ] E13. Are admin endpoints isolated and audited?

### Mandatory negative tests
- User A requests User B resource ID.
- Tenant A requests Tenant B data.
- Lower role calls admin endpoint directly.
- Hidden frontend button endpoint is called manually.
- Expired/revoked token is replayed.

---

## F. Web & Application Security

- [ ] F1. OWASP Top 10 risks are tested, not merely claimed.
- [ ] F2. SQL injection is prevented, including raw query paths.
- [ ] F3. XSS prevention is tested for stored and reflected content.
- [ ] F4. CSRF protection is correct for the authentication model.
- [ ] F5. SSRF paths are blocked.
- [ ] F6. Path traversal is blocked.
- [ ] F7. File upload type, size, MIME, extension, parsing, and execution behavior are constrained.
- [ ] F8. Zip bombs / decompression bombs are considered.
- [ ] F9. CSV/Excel formula injection is prevented in exports.
- [ ] F10. Security headers and CSP are appropriate.
- [ ] F11. Rate limits exist on login, OTP, password reset, expensive search, export, and abuse-sensitive routes.
- [ ] F12. Brute-force and credential stuffing protections are present.
- [ ] F13. Sensitive data is encrypted appropriately at rest and in transit.
- [ ] F14. Logs do not contain passwords, tokens, credentials, payment data, or unnecessary PII.
- [ ] F15. Dependency vulnerabilities are continuously scanned.

---

## G. File Storage & Object Security

- [ ] G1. Private files are private by default.
- [ ] G2. Object identifiers are not treated as authorization.
- [ ] G3. Download URLs are signed and short-lived where needed.
- [ ] G4. Uploads are scanned and constrained.
- [ ] G5. Orphan files are reconciled after failed DB transactions.
- [ ] G6. Deleting a DB record does not silently destroy required legal/audit files.
- [ ] G7. File metadata ownership is tenant-safe.

---

## H. Frontend State, UX Integrity & Data Freshness

- [ ] H1. The UI never displays an option that is not implemented correctly in the backend.
- [ ] H2. Unsupported features fail closed with a clear error instead of silently falling back.
- [ ] H3. Cached data has an explicit freshness policy.
- [ ] H4. Critical balances/statuses are not shown from stale cache without indication.
- [ ] H5. Double-click / retry / browser refresh cannot duplicate transactions.
- [ ] H6. Optimistic UI updates reconcile correctly after server failure.
- [ ] H7. Large tables use virtualization/pagination where needed.
- [ ] H8. Unsaved edits, conflicts, and multi-user editing are handled.
- [ ] H9. Form validation matches server rules but does not replace them.
- [ ] H10. Empty dashboards are not accepted as operational validation.

### Silent-lie rule
If the UI says "FIFO", "Paid", "Approved", "Encrypted", "Backed up", "Synced", or any other business/security claim, verify the exact backend path proving that claim.

---

## I. Performance & Scalability

- [ ] I1. Performance targets (SLO/SLA) are defined.
- [ ] I2. Slow endpoints are profiled using traces, not guessed.
- [ ] I3. N+1 queries are detected.
- [ ] I4. Database indexes match real query patterns.
- [ ] I5. Query plans are inspected for large tables.
- [ ] I6. Connection pool limits are configured relative to database capacity.
- [ ] I7. Large reports cannot starve transactional traffic.
- [ ] I8. Expensive exports run asynchronously when appropriate.
- [ ] I9. Cache invalidation rules are explicit.
