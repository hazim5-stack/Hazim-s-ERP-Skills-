- [ ] AQ3. Duplicate webhook events cannot duplicate payments, orders, stock, or notifications with side effects.
- [ ] AQ4. Message ordering assumptions are explicit.
- [ ] AQ5. Out-of-order events are rejected, buffered, versioned, or safely reconciled.
- [ ] AQ6. Poison messages have a dead-letter/quarantine strategy.
- [ ] AQ7. Retry policy includes bounded attempts or escalation strategy.
- [ ] AQ8. Exponential backoff and jitter are used where appropriate.
- [ ] AQ9. Retry storms cannot overload a recovering dependency.
- [ ] AQ10. Job visibility timeout/lease is longer than expected processing or safely extendable.
- [ ] AQ11. Worker crash after side effect but before acknowledgment does not duplicate the business action.
- [ ] AQ12. Scheduled jobs cannot run twice concurrently unless safe.
- [ ] AQ13. Clock/timezone assumptions in schedules are documented.
- [ ] AQ14. Webhook signatures are verified using raw canonical payload requirements.
- [ ] AQ15. Webhook replay windows/nonces/event IDs are handled.
- [ ] AQ16. External callback URLs are allowlisted or SSRF-protected where applicable.
- [ ] AQ17. Outbox records and delivery state are observable and recoverable.
- [ ] AQ18. Compensation logic is tested for partially completed distributed workflows.

# 17. Cache, Search Index & Derived-Data Consistency Gate

- [ ] CD1. The authoritative source of truth is documented for every cached/derived value.
- [ ] CD2. Cache invalidation rules are explicit.
- [ ] CD3. Stale cache cannot authorize an action after permission revocation.
- [ ] CD4. Stale cache cannot oversell inventory or violate financial invariants.
- [ ] CD5. Cache outages degrade safely instead of corrupting durable state.
- [ ] CD6. Cache key tenant/user scoping is correct.
- [ ] CD7. Cache stampede protection exists for expensive hot keys when needed.
- [ ] CD8. Search indexes are treated as derived data unless explicitly authoritative.
- [ ] CD9. Index lag is measured for "real-time" claims.
- [ ] CD10. Reindexing can be performed without losing authoritative records.
- [ ] CD11. Dashboard aggregates have a documented freshness contract.
- [ ] CD12. Derived counters can be rebuilt and reconciled from source events.

# 18. Privacy, Sensitive Data & Retention Gate

- [ ] PV1. Sensitive data classes are identified.
- [ ] PV2. Collection is limited to fields actually needed for the product purpose.
- [ ] PV3. Sensitive fields are excluded from routine logs and analytics unless justified.
- [ ] PV4. Data retention periods are defined.
- [ ] PV5. Deletion/anonymization behavior is defined where required.

# 19. Database Concurrency Deep-Dive

The auditor must not assume that a transaction automatically prevents logical races.

- [ ] DBX1. The isolation level used by each critical transaction is known.
- [ ] DBX2. Read-modify-write paths are reviewed for lost updates.
- [ ] DBX3. Predicate/range races are reviewed where existence checks precede insert/update.
- [ ] DBX4. Unique constraints close check-then-insert races.
- [ ] DBX5. Serialization/deadlock failures are retried only when retry is safe.
- [ ] DBX6. Retry loops are bounded and instrumented.
- [ ] DBX7. Lock acquisition order is consistent across multi-row/multi-table workflows.
- [ ] DBX8. Long transactions do not hold locks while waiting on remote APIs or user input.
- [ ] DBX9. Report queries cannot accidentally block critical writes for unacceptable periods.
- [ ] DBX10. Connection-pool exhaustion behavior is tested.
- [ ] DBX11. Replica lag is considered before reading after write from replicas.
- [ ] DBX12. Failover does not allow stale primary assumptions or duplicate leaders.
- [ ] DBX13. Database constraints are validated after bulk imports and migrations.
- [ ] DBX14. Bulk jobs respect the same invariants as normal API writes.

### PostgreSQL-specific note
When Serializable isolation is used, the application must correctly retry serialization failures; choosing Serializable without a retry strategy is incomplete.

# 20. AI-Generated Code Forensics

Search specifically for patterns frequently introduced by rushed AI-assisted development.

- [ ] AIF1. UI option exists with no backend implementation.
- [ ] AIF2. Placeholder branch silently returns success/default/empty result.
- [ ] AIF3. Catch block converts business failure into success or generic empty data.
- [ ] AIF4. TODO/FIXME marks a production-critical code path.
- [ ] AIF5. Mock/stub provider is enabled in production configuration.
- [ ] AIF6. Hard-coded demo user, role, tenant, date, currency, or identifier remains.
- [ ] AIF7. Generated migration drops/recreates data unnecessarily.
- [ ] AIF8. ORM schema says one thing while hand-written SQL assumes another.
- [ ] AIF9. Same enum/rule is independently duplicated in multiple layers.
- [ ] AIF10. Validation schema accepts states rejected later by database/domain logic.
- [ ] AIF11. "Temporary" bypass disables auth, rate limits, TLS verification, or signature verification.
- [ ] AIF12. Security library is configured with tutorial/development defaults.
- [ ] AIF13. Retry logic retries non-idempotent operations blindly.
- [ ] AIF14. Monetary computation converts Decimal to float/number mid-flow.
- [ ] AIF15. Time handling mixes local time, UTC, strings, and naive timestamps.
- [ ] AIF16. Silent fallback substitutes another algorithm when selected behavior is unimplemented.
- [ ] AIF17. Tests assert mocked implementation details but not business outcomes.
- [ ] AIF18. Generated tests reproduce the same incorrect assumption as generated production code.
- [ ] AIF19. Large test counts contain duplicated/template scenarios with weak assertions.
- [ ] AIF20. AI review claims are accepted without independent runtime evidence.

# 22. Release Decision Rules

The final result must be one of:
- **PRODUCTION READY**
- **CONDITIONALLY READY**
- **PRE-PRODUCTION ONLY**
- **PROTOTYPE ONLY**
- **NOT PRODUCTION READY**

## Mandatory stop-ship examples
A release is NOT PRODUCTION READY when any unresolved issue can plausibly cause:
- unauthorized cross-user or cross-tenant access,
- arbitrary privilege escalation,
- secret/key exposure enabling system compromise,
- unbounded duplicate payment/order/inventory effects,
- silent financial misstatement,
- unrecoverable primary data loss,
- migrations that can destroy production data without tested recovery,
- inability to restore critical data within required RPO/RTO,
- known remote code execution or equivalent critical exploit,
- or silent substitution of a materially different business algorithm.

## Conditional readiness
CONDITIONALLY READY may be used only when:
- no Critical findings remain,
- High findings have explicit risk acceptance or near-term owners,
- restore evidence exists,
- core security boundaries are proven,
- and the claimed product scope matches what was actually tested.

Never use a numerical score to override a stop-ship rule.

# 24. Final Auditor Behavior

The auditor must behave like an independent release gate, not a code-generation assistant.

- [ ] FB1. Do not modify code before capturing the baseline findings unless explicitly asked to repair while auditing.
- [ ] FB2. When repairs are requested, preserve a before/after finding ledger.
- [ ] FB3. Fix root causes before cosmetic symptoms.
- [ ] FB4. Re-run the smallest decisive test after each critical fix.
- [ ] FB5. Re-run the complete critical-path suite before changing the final verdict.
- [ ] FB6. Do not weaken a test merely to make CI green.
- [ ] FB7. Do not delete constraints to make a migration pass without proving semantic equivalence.
- [ ] FB8. Do not disable security middleware to unblock development.
- [ ] FB9. Do not change business rules to match broken implementation without explicit domain approval.
- [ ] FB10. End with remaining unknowns, not only known defects.

**The audit is complete only when the reviewer can explain not merely what the software does when everything works, but what prevents it from lying, duplicating, leaking, corrupting, or becoming unrecoverable when things fail.**

# 25. Principle

**A production system is not defined by how much code it contains. It is defined by the invalid states it makes impossible, the failures it survives, the business rules it proves, and the history it can reconcile and recover.**
