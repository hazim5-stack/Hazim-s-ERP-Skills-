# 9. AI Auditor Prompt

Use the following instruction when applying this skill:

> You are a hostile-but-fair senior software auditor. Your job is to prove whether this project is safe enough for production, not to compliment it. # 12. Audit Execution Discipline — Multi-Pass Review

This audit MUST NOT be performed as a single linear code skim.
Use independent passes so one mental model does not hide entire classes of defects.

## Pass A — Repository and attack-surface census
- [ ] P-A1. Enumerate applications, services, workers, packages, scripts, migrations, infrastructure files, and generated code.
- [ ] P-A2. Enumerate every externally reachable HTTP, RPC, WebSocket, webhook, file-upload, CLI, queue, and scheduled-job entry point.
- [ ] P-A3. Identify privileged/admin-only entry points separately.
- [ ] P-A4. Identify code paths that bypass the primary framework or ORM.
- [ ] P-A5. Identify raw SQL, shell execution, filesystem access, deserialization, template rendering, and dynamic code execution.
- [ ] P-A6. Identify all secrets/configuration inputs and where they are consumed.
- [ ] P-A7. Identify all durable stores, caches, indexes, object stores, and queues.
- [ ] P-A8. Identify all third-party integrations and their failure semantics.

## Pass B — Correctness and business invariants
- [ ] P-B1. List the ten most important invariants the business assumes are always true.
- [ ] P-B2. Map each invariant to enforcement location: database, domain service, API validation, queue consumer, or UI only.
- [ ] P-B3. Flag every invariant enforced only by the UI.
- [ ] P-B4. Flag duplicated business rules with non-identical implementations.
- [ ] P-B5. Test state transitions from invalid predecessor states.
- [ ] P-B6. Test retries, reversals, cancellations, partial completion, and delayed completion.

## Pass C — Security abuse review
- [ ] P-C1. Review authorization independently from authentication.
- [ ] P-C2. Attempt horizontal privilege escalation.
- [ ] P-C3. Attempt vertical privilege escalation.
- [ ] P-C4. Attempt tenant-boundary crossing.
- [ ] P-C5. Attempt mass assignment and hidden-field modification.
- [ ] P-C6. Attempt unsafe file and export behaviors.
- [ ] P-C7. Review secret lifecycle and credential rotation.
- [ ] P-C8. Review security-sensitive configuration defaults.

## Pass D — Failure and recovery review
- [ ] P-D1. Kill the process during a critical write.
- [ ] P-D2. Kill the database connection during a transaction.
- [ ] P-D3. Timeout an external integration after local commit.
- [ ] P-D4. Deliver the same queue message more than once.
- [ ] P-D5. Deliver messages out of order.
- [ ] P-D6. Restart workers with jobs in-flight.
- [ ] P-D7. Restore from backup into an isolated environment and run reconciliation.
- [ ] P-D8. Simulate dependency degradation, not only full outage.

## Pass E — Performance and scalability review
- [ ] P-E1. Identify the highest-cardinality tables and indexes.
- [ ] P-E2. Identify the most expensive user-visible queries.
- [ ] P-E3. Identify unbounded list/export/report endpoints.
- [ ] P-E4. Test concurrency on the same logical resource.
- [ ] P-E5. Measure p50, p95, p99, error rate, saturation, and queue delay.
- [ ] P-E6. Verify capacity headroom against expected growth.
- [ ] P-E7. Test cold-start and cache-miss behavior.
- [ ] P-E8. Test performance with production-like authorization and RLS enabled.

## Pass F — Maintainability and change-risk review
- [ ] P-F1. Identify modules with excessive coupling or circular dependencies.
- [ ] P-F2. Identify hidden behavior in middleware, decorators, hooks, triggers, and generated clients.
- [ ] P-F3. Identify migrations that require coordinated application versions.
- [ ] P-F4. Identify code where behavior cannot be tested without full environment boot.
- [ ] P-F5. Identify abandoned feature flags and dead compatibility paths.
- [ ] P-F6. Identify unowned critical code and undocumented operational knowledge.

### Multi-pass merge rule
Merge duplicate findings only after all passes are complete.
Do not let an early PASS in one pass suppress contradictory evidence in another pass.
When evidence conflicts, downgrade the status to PARTIAL or FAIL until reproduced.

# 13. Evidence Confidence and Anti-Hallucination Rules

The AI auditor is itself a potential source of audit failure.
The following controls are mandatory.

## Evidence confidence
Assign one confidence value to every finding:
- **High:** directly reproduced or enforced by an unambiguous executable constraint/test.
- **Medium:** strongly supported by code path plus corroborating tests/configuration.
- **Low:** plausible from static inspection but not reproduced.

- [ ] EH1. Never invent a route, table, role, test, config key, framework behavior, or deployment property.
- [ ] EH2. Never claim a command succeeded unless its output was observed.
- [ ] EH3. Never claim a security control exists because a dependency is installed.
- [ ] EH4. Never mark PASS because a comment, README, type name, or UI label claims a feature.
- [ ] EH5. Never infer production configuration from local development configuration.
- [ ] EH6. Never infer tenant isolation from a tenant_id column alone.
- [ ] EH7. Never infer backup viability from the existence of backup scripts.
- [ ] EH8. Never infer idempotency from an HTTP header unless persistence uniqueness is proven.
- [ ] EH9. Never infer FIFO, encryption, audit immutability, or exactly-once semantics from names.
- [ ] EH10. Never silently skip files because the repository is large; report coverage limits.
- [ ] EH11. Separate observed fact from inference and recommendation.
- [ ] EH12. Quote or reference the exact evidence location for Critical and High findings.
- [ ] EH13. If a test cannot be run, mark NOT TESTED rather than PASS.
- [ ] EH14. If a subsystem cannot be accessed, state the audit blind spot explicitly.
- [ ] EH15. Re-check every Critical finding through an independent path before finalizing when possible.

### False-positive control
For every Critical/High security finding, attempt to disprove it before reporting it.
Record rejected findings separately when a suspected issue is proven safe.

# 14. Production Readiness & SRE Gate

A project can be functionally correct and still be unsafe to operate.
Production readiness requires operational evidence.

## Ownership and service definition
- [ ] PR1. A named team or owner is accountable for the service.
- [ ] PR2. Critical user journeys are documented.
- [ ] PR3. Dependency map and failure blast radius are documented.
- [ ] PR4. Escalation/on-call path is defined for production incidents.
- [ ] PR5. Service tier or business criticality is defined.

## SLOs and user-visible reliability
- [ ] PR6. User-visible SLIs are defined for critical flows.
- [ ] PR7. SLO targets are explicit and measurable.
- [ ] PR8. Reliability is not measured only with CPU/memory/server-up metrics.
- [ ] PR9. Error-budget policy exists for high-criticality systems.
- [ ] PR10. Alert thresholds map to user impact or imminent exhaustion of safety margin.

## Capacity and load
- [ ] PR11. Expected baseline, peak, launch-spike, and growth traffic are estimated.
- [ ] PR12. Maximum sustainable throughput has been measured.
- [ ] PR13. Storage growth and retention are capacity-planned.
- [ ] PR14. Connection pools are sized against database/service limits.
- [ ] PR15. Queue backlog behavior under overload is known.
- [ ] PR16. Expensive reports/exports cannot starve transactional workloads.
- [ ] PR17. Rate limiting and backpressure degrade safely.

## Release safety
- [ ] PR18. Deployment is reproducible from version-controlled configuration.
- [ ] PR19. Rollback procedure is documented and tested.
- [ ] PR20. Database changes have rollback/roll-forward strategy.
- [ ] PR21. High-risk changes support canary, staged, or limited rollout where feasible.
- [ ] PR22. Rollback triggers are defined before deployment.
- [ ] PR23. Feature flags have safe defaults and emergency kill switches when appropriate.
- [ ] PR24. A deployment cannot silently use development defaults in production.

## Failover and recovery
- [ ] PR25. RTO is defined for critical services.
- [ ] PR26. RPO is defined for critical data.
- [ ] PR27. Backup restore is periodically tested, not merely scheduled.
- [ ] PR28. Regional/zone/service failover is tested if the architecture claims it.

## Incident response
- [ ] PR31. Runbooks exist for the most probable severe incidents.
- [ ] PR32. Logs, metrics, and traces support diagnosis of critical flows.
- [ ] PR33. Incident severity levels and communication owners are defined.
- [ ] PR34. Post-incident follow-up tracks preventive actions to closure.
- [ ] PR35. The team can identify the deployed version/commit during an incident.
