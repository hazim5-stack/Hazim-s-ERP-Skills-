# Hazim Batwa's Engineering Skill for Building a Mini ERP Project for Small and Micro Businesses

## Purpose
Use this skill **before implementation** to design a production-grade ERP or enterprise operations platform.

This skill forces the AI to plan the business system before generating CRUD screens or database tables. It is intended for ERP, manufacturing, inventory, accounting, procurement, sales, quality, warehouse, HR, asset, workflow, and enterprise SaaS projects.

The output of this skill is a build-ready engineering plan, not code.

---

# 1. Planner Operating Rules

## 1.1 Core stance
Never start with screens.
Start with business events, invariants, ledgers, state transitions, permissions, failure modes, and reconciliation rules.

Do not treat these as proof of ERP completeness:
- menu names,
- dashboard cards,
- number of tables,
- framework choices,
- number of roles,
- number of API endpoints,
- generated diagrams,
- or AI confidence.

## 1.2 Planning objective
Before implementation, every critical workflow must define:
1. business trigger,
2. preconditions,
3. state transition,
4. authoritative source of truth,
5. database invariants,
6. financial consequence,
7. inventory consequence,
8. authorization rule,
9. concurrency behavior,
10. idempotency behavior,
11. external side effects,
12. rollback/reversal behavior,
13. audit event,
14. report impact,
15. acceptance tests,
16. failure tests.

## 1.3 No silent assumptions
If a business rule is unknown, mark it:
`DOMAIN DECISION REQUIRED`

Never invent:
- accounting policy,
- tax rule,
- inventory valuation method,
- period-close behavior,
- approval authority,
- manufacturing costing method,
- regulatory retention,
- or segregation-of-duties policy.

## 1.4 Planning artifact rule
Each major design decision must produce at least one concrete artifact:
- ADR,
- domain model,
- state machine,
- event catalog,
- sequence diagram,
- ERD,
- permission matrix,
- accounting posting matrix,
- inventory movement matrix,
- API contract,
- acceptance-test matrix,
- deployment diagram,
- or runbook.

# 2. Project Discovery

## 2.1 Business scope
Define:
- legal entity count,
- branches,
- warehouses,
- plants,
- currencies,
- fiscal calendars,
- countries,
- tax regimes,
- languages,
- user count,
- peak concurrent users,
- expected transaction volume,
- required availability,
- RPO,
- RTO.

## 2.2 Stakeholder map
Identify domain owners for:
- finance,
- cost accounting,
- procurement,
- warehouse,
- production planning,
- manufacturing execution,
- quality,
- sales,
- HR,
- IT/security,
- management reporting.

No critical domain may be designed only from developer assumptions.

## 2.3 System boundary
Document what the ERP owns versus external systems:
- ecommerce,
- payment gateways,
- banks,
- payroll,
- shipping,
- customs,
- MES,
- SCADA,
- barcode devices,
- weighing scales,
- CRM,
- document management,
- BI,
- identity provider.

For each integration define:
- direction,
- protocol,
- authentication,
- retry,
- idempotency,
- timeout,
- reconciliation,
- ownership of truth.

# 3. Domain Decomposition

## 3.1 Required bounded contexts
Evaluate whether the project requires separate domain boundaries for:
- Identity & Access,
- Organization,
- Master Data,
- Purchasing,
- Receiving,
- Inventory,
- Warehouse,
- Quality,
- Manufacturing,
- Costing,
- Sales,
- Accounts Receivable,
- Accounts Payable,
- General Ledger,
- Fixed Assets,
- Treasury,
- Tax,
- Reporting,
- Audit,
- Files,
- Notifications,
- Integrations.

## 3.2 Source-of-truth matrix
For every important fact identify exactly one authoritative source.
Examples:
- stock quantity,
- reserved quantity,
- inventory value,
- open AP balance,
- customer balance,
- production WIP,
- invoice state,
- payment state,
- lot expiry,
- approval status.

Derived views may cache facts but must never become competing truth.

## 3.3 State-machine requirement
Model critical entities as explicit state machines.
Examples:
- purchase order,
- goods receipt,
- supplier invoice,
- sales order,
- shipment,
- customer invoice,
- payment,
- manufacturing order,
- quality inspection,
- period close.

For each transition define:
- allowed source states,
- destination state,
- actor permission,
- validation,
- generated ledger entries,
- generated stock movements,
- reversal rule.

# 4. Event Model Before Data Model

## 4.1 Business event catalog
Create an event catalog before designing tables.
Minimum examples:
- PurchaseOrderApproved
- GoodsReceived
- QualityAccepted
- QualityRejected
- SupplierInvoicePosted
- InventoryReserved
- InventoryIssued
- InventoryReturned
- ManufacturingStarted
- ProductionCompleted
- SalesOrderApproved
- GoodsShipped
- CustomerInvoicePosted
- PaymentReceived
- AccountingPeriodClosed
- JournalReversed

## 4.2 Event semantics
For every event answer:
- what happened in the real world?
- when did it happen?
- when was it recorded?
- can it be corrected?
- can it be reversed?
- does reversal preserve history?
- what downstream ledgers change?

## 4.3 Posting moment
Never defer posting semantics to later implementation.
Define exactly when:
- physical inventory changes,
- inventory accounting changes,
- AP liability appears,
- AR receivable appears,
- revenue is recognized,
- WIP appears,
- manufacturing variance appears.
